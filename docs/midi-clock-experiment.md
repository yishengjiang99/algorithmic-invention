# MIDI clock: raw timing vs jitter-resistant estimation

Generated by `node scripts/midi-clock-experiment.mjs` (do not edit by hand; `npm test` fails if this file is stale).
Every number below is measured by that script from seeded synthetic traces; nothing is hand-entered.

## Question

Can a Web MIDI clock follower get a usable tempo and beat phase from the timestamps of F8 messages when those timestamps are noisy, or is the last interval enough?

## Hypothesis (fixed before measuring)

The rolling-median + phase-correction estimator ("filtered") settles within 2 s, with BPM error below 0.5 and p95 beat-phase error below 5 ms. The last-interval estimate is the baseline.

## Method

- Trace: 120 BPM, 24 clocks per beat (ideal period 20.8333 ms), 120 s, 5761 ideal clocks.
- Timestamp jitter: uniform ±3 ms on every message.
- Missing clocks: each message is dropped with probability 1% (independent).
- Delivery delay: every 64th clock is stamped 20 ms late. At 120 BPM a tick is 20.83 ms, so a delayed clock is often reordered behind its successor; observed timestamps are sorted, as a receiver would see them.
- PRNG: mulberry32. Headline seed 20261018 (5703 messages delivered). A 20-seed sweep (seeds 1 to 20) checks the headline is not a lucky draw.
- Causal replay: at every 1 ms instant the estimator has only seen messages stamped at or before that instant. Phase error is the distance (wrapped to one beat, in ms) between the estimator's tick position and the true tick position at that instant; BPM error is |estimate − 120|.
- Steady-state statistics use t ≥ 2 s. **Settling time** is one millisecond after the last instant at which phase error ≥ 5 ms or BPM error ≥ 0.5 (or no estimate exists); "never" means it was still violating at the end of the trace. The BPM gate is the stricter **maximum** over steady state, not p95.
- Resynchronizations: *internal* = hard re-anchors the estimator reports (gap too long, tempo step, phase target off by more than 15 ms). *Visible phase jumps* = clock arrivals where the predicted tick position moved by more than 5 ms, measured from outside, which is meaningful for the baseline because it re-anchors on every message.
- Filtered estimator parameters (defaults, untuned): capacity=256, span=48, window=48, dupFraction=0.4, maxGapTicks=96, phaseGain=0.25, resyncPhaseMs=15, sustain=8, tempoStepFraction=0.06, readyClocks=48.

## Selection

Selected estimator: **filtered**. It meets all three thresholds on the headline seed and on all 20 sweep seeds.

Why the baseline fails (measured above): one ±3 ms timestamp error moves a single interval by up to ±6 ms, which is up to ±29% of a 20.83 ms tick, so its median BPM error is 10.5 and its p95 is 34.9. When a delayed clock is reordered behind its successor the two stamps are almost equal and the "last interval" is close to zero, which explains why the maximum BPM error is astronomically large (62404); a dropped clock makes the interval double and halves the reading. It also re-anchors its phase on every message (1473 visible jumps above 5 ms) and its tick counter counts messages rather than ticks, so every missing clock shifts phase by one tick (20.8 ms) permanently. Its phase error wraps at half a beat (250 ms), and a median of 129 ms means it is effectively unsynchronised.

## Limits (what this does not show)

- Synthetic traces only. Real devices and OS MIDI stacks have non-uniform jitter (bursts, quantised stamps), which this does not model.
- Constant tempo. Tempo changes (the 120 → 90 BPM step) are covered by the unit tests in `src/lib/midi-clock/` (see `docs/midi-clock-follower.md`), not by this experiment.
- The estimator parameters were not tuned against these seeds; they are the module defaults.
- Phase error is measured against the generator's ideal tick grid, so it excludes audio output latency and the performance.now to AudioContext conversion error (see `docs/midi-clock-follower.md`).
